# 🔁 GitOps

Связано с [[🗺️ DevOps MOC]]


Подход к деплою, где **git-репозиторий — единственный источник правды** о том, что должно быть развёрнуто. Не "запусти скрипт, который задеплоит", а "приведи кластер в состояние, описанное в этом репозитории".

## Принципы (по OpenGitOps)

1. **Declarative** — всё описано декларативно (YAML-манифесты, Helm-чарты), а не как последовательность команд.
2. **Versioned & Immutable** — состояние хранится в git → есть история, diff, code review, откат через `git revert`.
3. **Pulled automatically** — агент внутри кластера сам тянет изменения из git, а не внешняя система стучится в кластер.
4. **Continuously reconciled** — агент постоянно сверяет актуальное состояние кластера с тем, что в git, и лечит любой дрейф (drift).

## Push-based CI/CD vs Pull-based GitOps

```
Push-модель (классический CI/CD):
  CI-раннер → kubectl apply / helm upgrade → кластер
  (раннеру нужен прямой доступ/креды в прод-кластер)

Pull-модель (GitOps):
  git repo (желаемое состояние) ←--- сверяет ---  агент (ArgoCD/Flux) внутри кластера
  агент сам применяет diff, кластеру не нужно "открывать" доступ снаружи
```

Главный практический выигрыш pull-модели: **прод-креды не покидают кластер** — CI-раннеру для деплоя больше не нужен kubeconfig от продакшена, он просто пушит новый манифест/тег в git.

## Два репозитория (частый паттерн)

- **App repo** — исходный код приложения + Dockerfile. CI здесь собирает и пушит image.
- **Config/GitOps repo** — только манифесты/чарты с конкретными versions/tags. CI из app repo обновляет тут тег image (`image.tag: v1.4.1`) через коммит/PR — а дальше ArgoCD/Flux сами подхватывают изменение.

Так CI (сборка) и CD (деплой) разделены: одна система собирает, другая — только следит за состоянием git и приводит кластер в соответствие.

## Инструменты

| Инструмент | Особенность |
|---|---|
| **ArgoCD** — 🐙ArgoCD | UI из коробки, Application CRD, App of Apps, лучше всего заходит для многих сервисов/команд |
| **Flux** | легче, глубже интегрирован с Helm/Kustomize нативно, меньше UI из коробки |
| **GitLab CI** — 🦊GitLab CI | не GitOps-агент сам по себе, но обычно и есть тот, кто пишет новый тег в config-repo, и может быть настроен на push-based деплой как альтернатива |

## Типичный GitOps-флоу

```
1. Разработчик мержит PR в app repo
2. GitLab CI: тесты → сборка Docker image → push в registry с тегом $CI_COMMIT_SHA
3. GitLab CI (последний job): клонирует config repo,
   меняет image.tag в values.yaml/kustomization.yaml, коммитит и пушит
4. ArgoCD видит изменение в config repo (poll раз в N сек или webhook)
5. ArgoCD сравнивает desired (git) vs live (кластер) → видит diff → применяет
6. Кластер приведён в соответствие; в UI ArgoCD видно Synced/Healthy
```

> [!tip] Когда GitOps того стоит
> Если у тебя один сервис и один сервер — оверхед на два репозитория и агент в кластере не оправдан, обычный CI/CD с `kubectl apply` в конце пайплайна (🔄CI-CD Pipelines) проще. GitOps раскрывается на масштабе: много сервисов/кластеров/окружений, где важны аудит изменений, единообразный процесс отката и разделение "кто может менять код" от "кто может менять прод".

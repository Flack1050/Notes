# ⚙️ Процессы, память и файловая система

Связано: [[🧠Архитектура Linux]] · [[🥾Загрузка и init]] · [[🐳Docker]]

## Процессы

Каждый процесс в Linux (кроме PID 1) порождается через `fork()` (клонирование текущего процесса) + обычно сразу `execve()` (замена своего кода на код новой программы).

```bash
ps aux                      # все процессы
ps -ef --forest               # дерево процессов (кто чей родитель)
pstree                          # то же самое, нагляднее
top / htop                        # живой мониторинг

kill -15 <pid>                      # SIGTERM — вежливо попросить завершиться
kill -9 <pid>                        # SIGKILL — убить немедленно, без шанса прибраться
kill -l                                # список всех доступных сигналов
```

### Состояния процесса

| Состояние | Обозначение в `ps` | Значение |
|---|---|---|
| Running | `R` | выполняется или готов к выполнению |
| Sleeping | `S` | ждёт события (ввод, таймер) — прерываемый сон |
| Uninterruptible sleep | `D` | ждёт I/O (обычно диск) — нельзя прервать сигналом |
| Stopped | `T` | остановлен (Ctrl+Z или SIGSTOP) |
| Zombie | `Z` | завершился, но родитель ещё не прочитал его код возврата (`wait()`) |

> [!note] Zombie-процессы
> Zombie не потребляет ресурсов (кроме записи в таблице процессов) — он уже мёртв, просто ждёт, пока родитель заберёт его exit-код. Если родитель никогда не вызывает `wait()`, зомби накапливаются, пока не завершится сам родитель (тогда зомби "усыновляет" PID 1 и тот его подчищает).

### Планировщик (scheduler)

Ядро решает, какой процесс получит CPU в следующий момент времени через **completely fair scheduler (CFS)** по умолчанию — старается дать каждому процессу "справедливую" долю времени CPU с учётом **nice-значения** (приоритета):

```bash
nice -n 10 ./heavy-script.sh      # запустить с более низким приоритетом (диапазон -20..19)
renice -n 5 -p <pid>                 # изменить приоритет уже запущенного процесса
```

## Namespaces и cgroups — то, на чём держится Docker

Это не отдельная "виртуализация" — обычные механизмы ядра Linux, которые [[🐳Docker]] использует для изоляции:

- **Namespaces** — изолируют, что процесс **видит**:
  - `PID` namespace — свой список процессов (PID 1 внутри контейнера — не настоящий PID 1 хоста).
  - `NET` namespace — своя сетевая конфигурация (интерфейсы, таблица маршрутизации).
  - `MNT` namespace — своё дерево точек монтирования.
  - `UTS` namespace — своё hostname.
  - `IPC`, `USER` namespace — своя IPC-очередь, своё отображение UID.
- **cgroups** (control groups) — ограничивают, сколько ресурсов процесс **может использовать** (CPU, память, I/O), и позволяют группировать процессы для учёта и лимитов.

```bash
lsns                              # посмотреть активные namespaces в системе
cat /sys/fs/cgroup/memory.max     # лимит памяти для текущей cgroup (cgroup v2)
```

Контейнер — это по сути обычный Linux-процесс, просто запущенный в своём наборе namespaces + ограниченный через cgroup. Никакой отдельной "виртуальной машины" нет — именно поэтому контейнеры стартуют за миллисекунды, а не как полноценная VM.

## Память

```bash
free -h                       # сколько RAM/swap используется
vmstat 1                        # статистика памяти/CPU в реальном времени
cat /proc/meminfo                 # подробная разбивка
```

- **Виртуальная память** — каждый процесс видит свой собственный "как будто бесконечный" адресный диапазон; ядро через **MMU** (Memory Management Unit процессора) транслирует виртуальные адреса в реальные физические страницы RAM. Это даёт изоляцию (один процесс не может напрямую читать память другого) и позволяет обманом "расширять" память через swap.
- **Swap** — область на диске, куда ядро выгружает редко используемые страницы памяти, когда RAM заканчивается. Медленнее RAM на порядки, но не даёт системе упасть при нехватке памяти (вместо этого тормозит).
- **OOM Killer** — если даже со swap памяти не хватает, ядро убивает процесс, который "съедает" больше всего памяти, чтобы спасти систему (`dmesg | grep -i "out of memory"` покажет, если это происходило).

## Файловая система

### FHS (Filesystem Hierarchy Standard) — куда что класть

| Путь | Что там |
|---|---|
| `/bin`, `/usr/bin` | исполняемые файлы (в современных дистрибутивах `/bin` — симлинк на `/usr/bin`) |
| `/etc` | конфиги |
| `/var` | изменяемые данные: логи (`/var/log`), кэш, базы данных |
| `/home` | домашние директории пользователей |
| `/tmp` | временные файлы, обычно очищается при перезагрузке |
| `/opt` | сторонний софт не из пакетного менеджера |
| `/proc` | виртуальная ФС — живое состояние ядра/процессов (не реальные файлы на диске!) |
| `/sys` | виртуальная ФС — интерфейс к устройствам и параметрам ядра |
| `/dev` | файлы устройств (`/dev/sda`, `/dev/null`, `/dev/tty`) |

`/proc` и `/sys` — не файлы на диске, а "окно" в структуры данных ядра в реальном времени:

```bash
cat /proc/cpuinfo          # инфа о CPU прямо из ядра
cat /proc/<pid>/status       # статус конкретного процесса
echo 1 > /sys/class/leds/.../brightness   # пример управления железом через sysfs
```

### Inode

Каждый файл в Linux — это **inode** (метаданные: права, владелец, размер, указатели на блоки данных) + имя файла — отдельная запись в директории, которая на этот inode ссылается. Поэтому в Linux возможны **hard links** — несколько имён файлов, указывающих на один и тот же inode:

```bash
ls -i file.txt                # показать номер inode
ln file.txt hardlink.txt         # hard link — тот же inode, данные общие
ln -s file.txt symlink.txt         # symlink — отдельный файл, просто хранит путь
df -i                                # сколько inode'ов использовано/свободно (да, они тоже кончаются!)
```

### Права доступа

```bash
ls -l file.txt
# -rw-r--r--  1 user group  1234 Jan 1 12:00 file.txt
#  ^^^ ^^^ ^^^
#  owner group others

chmod 755 script.sh         # rwx r-x r-x — owner: всё, остальные: читать+выполнять
chmod u+x script.sh           # добавить право на выполнение владельцу
chown user:group file.txt        # сменить владельца и группу
```

- `r` (4) — читать, `w` (2) — писать, `x` (1) — выполнять (для директорий: заходить внутрь/листинг).
- Специальные биты: **setuid** (4000, запустить с правами владельца файла, а не запустившего), **setgid** (2000), **sticky bit** (1000, в `/tmp` — удалять файл может только его владелец, даже если у всех есть права на запись в саму директорию).

## Монтирование

```bash
mount                             # что сейчас смонтировано
mount /dev/sdb1 /mnt/usb            # смонтировать вручную
umount /mnt/usb
lsblk                                 # дерево дисков/разделов
cat /etc/fstab                         # что монтируется автоматически при загрузке
```
